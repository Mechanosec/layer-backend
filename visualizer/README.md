# Візуалізатор

Наочне пояснення того, як залишок з магазину стає кількістю, яку бачить покупець на
сайті. Зроблено для менеджера, а не для розробника: жодних логів і жодного JSON —
конвеєр, паперова лента розрахунку і журнал.

Це **вітрина над сервісом layer**, а не окремий продукт. Своїх даних вона не має:
усе, що на екрані, приходить з реального сервісу.

## Що показує

**Конвеєр** — шість стадій, які проходить одне повідомлення: Business Central →
Kafka → журнал подій → розрахунок → черга на сайт → сайт. Кожна стадія підписана
звичайною мовою і показує своє число. Коли зі стенду надсилають подію, по конвеєру
проходить хвиля — видно, що саме зрушилось.

**Лента розрахунку** — та сама формула, але у вигляді інвентаризаційної ленти: рядок
на кожен магазин, перекреслені ті, що не віддають товар в онлайн, нижче вирахування,
у підсумку — число на сайті. Це головний артефакт: його можна читати згори вниз і
сперечатися з ним.

**Сторона ECOM** — кількість в ордерах «Новий» задається тут, бо ордери справді
живуть в ECOM. Тут же можна вимкнути ECOM і побачити, що робить сервіс, коли не може
підтвердити резерв: бере останнє відоме значення, помічає число як непідтверджене,
затримує підвищення залишку й повторює спробу.

**Журнал** — в один список, що прийшло зі складу (◀) і що поїхало на сайт (▶).

## Як запустити

Однією командою з кореня репозиторію — вона підніме все, включно з цією сторінкою:

```bash
cd ..
./start-demo.sh
```

Браузер відкриється сам на http://localhost:5173. `Ctrl+C` зупиняє все.

Якщо сервіс уже працює десь окремо, сторінку можна підняти саму:

```bash
pnpm install
pnpm dev
```

Обидва сервіси проксіюються dev-сервером (`/api/layer` і `/api/ecom`), тому браузер
робить запити на одне походження — налаштовувати нічого не треба. Адреси можна
перебити змінними `LAYER_API_URL` і `MOCK_ECOM_URL`.

## Демонстрація за дві хвилини

1. **Звідки береться число.** Надішліть повний залишок `10` у магазин `0119`, потім
   `5` у `0120`, потім `100` у `0121` (склад). На ленті видно: у суму пішло 15, бо
   склад в онлайн не віддає. Мінус страховий запас 2, мінус ордери — і це число
   поїхало на сайт.
2. **Продали в магазині.** Тип «Зміна залишку», магазин `0119`, `-3`. Сайт одразу
   бачить менше.
3. **Хтось замовив онлайн.** Поставте «В ордерах Новий» = `4` і натисніть
   «Перерахувати». Доступне на сайті впало на 4, хоча на складі нічого не змінилось.
4. **ECOM ліг.** «Вимкнути ECOM», потім надішліть залишок `40` у `0119`. Сервіс
   порахував 39, але на сайт не віддав — підвищувати доступну кількість на
   непідтвердженому резерві небезпечно. Число на ленті помічене, лічильники
   «непідтверджені» і «чекає» зросли.
5. **ECOM повернувся.** «Увімкнути ECOM» і трохи почекати. Сервіс перерахує сам, без
   жодної нової події зі складу, і відправить число на сайт.

## Стек

Vite + React + TypeScript + Tailwind v4. Шрифти IBM Plex Sans / Mono локально через
`@fontsource` (з кириличними підмножинами), тому сторінка працює без інтернету.

```
src/
├── api/          типи та клієнт до layer-backend і заглушки ECOM
├── components/   Conveyor, ReceiptTape, StandPanel, EcomStand, ActivityLog
└── lib/          форматування часу та відмінків
```

Дані оновлюються опитуванням раз на 1,5 с — для демонстрації достатньо, і немає
жодного власного стану, який міг би розійтися з сервісом.

## Що тут навмисно не зроблено

Немає авторизації, збереження налаштувань і власної бази. Сторінка не є джерелом
правди ні для чого: усі кнопки лише викликають API сервісу. «Вимкнути ECOM» керує
заглушкою `../tools/mock-ecom.mjs`, а не справжнім ECOM.
